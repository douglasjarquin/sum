Goal Capsule

Objective. A person overseeing several projects can find every decision and important exception without reading a stream of routine coordinator updates.

Means. Shared presentation semantics, a grouped overview, recipient wake episodes, and evidence-derived digests (KTD1, KTD3, KTD5, KTD8).

Authority. Explicit user instructions govern scope and approval; the issue contracts govern product behavior; R-IDs below own requirements and KTDs own mechanisms. Source records remain authoritative. A plan, a displayed item, and a notification grant no execution or merge permission.

Execution profile. Nine implementation units across the roadmap’s five serial review boundaries. Each child ships focused tests. The final child owns the combined replay. Development uses isolated checkouts and temporary lab state.

Stop conditions. Stop implementation for a product-scope conflict, loss of a canonical obligation, inability to preserve uncertain attempts, or a prerequisite that would require live configuration changes. Unsupported native display capabilities select the documented fallback.

Finish and ship. Each worker verifies its candidate; coordinator verification and independent review remain separate. A human merges these sum changes. Deployment and live enablement require a later user decision.

Product Contract

Summary

Plan the full quiet-coordinator roadmap: separate required processing from human presentation, group saved operational state by project, coalesce routine wake-ups across passes, and report factory outcomes from evidence.

Problem Frame

The owner reports that concurrent workers and factories make the coordinator pane noisy. Existing code batches returns within a delivery pass, but a later new return can cause another prompt. Some status consumers also count an answered question as a human decision. The source findings explain plausible sources of noise; they are not a reproduced production benchmark.

Actors

  • A1. The user supplies instructions, answers actual decisions, and controls enablement and merge authority.
  • A2. The single coordinator processes global obligations and reports meaningful outcomes.
  • A3. Worker and review agents submit source records and retain their existing responsibilities.
  • A4. Sum derives views and submits eligible notices; Herdr owns panes and agent lifecycle.

Acceptance Examples

  • AE1. Twelve concurrent routine returns precede consumption: one eligible routine prompt is submitted and all twelve obligations remain retrievable. Covers R1, R9, R17.
  • AE2. A wake originally mentions A; a later snapshot includes A+B and omits C. Explicit consumption covers A+B only, leaves B’s attempt unchanged, and leaves C eligible for a subsequent supported pass. Covers R9, R10.
  • AE3. A question appears behind a routine wake. It gets a safe priority attempt once; after a real answer it leaves the human-decision count while worker application remains owed. Covers R2, R11, R13.
  • AE4. While viewing project X, project Y gains a question and a third task is unreadable. X stays focused; global known decisions and incomplete-source warnings remain visible. Covers R3, R7, R16.
  • AE5. A merge request succeeds but no saved merged observation exists. The digest cannot say merged. After observed merge and lane release, retained task evidence can still support a project outcome. Covers R14, R15.

Success Criteria

The deterministic capable-runtime burst in AE1 has exactly one routine prompt before consumption, with zero lost canonical obligations and zero read-side writes. The integrated replay reports baseline/candidate counts and actual reductions without substituting fewer reports for fewer interruptions. A native/harness demonstration is separately recorded as run or not-run; simulated output does not prove agent narration compliance.

Scope Boundaries

This covers #239, #241, #240a, #240b, and #242. Existing worker verification, coordinator verification, independent review, capacity, strict cleanup, and authorized factory gates remain governing contracts under R1 and R16.

Excluded: another coordinator or manager, daemon/ticker/scheduler, event broker/database, web dashboard, general policy registry, model classifier/summarizer, transcript rewriting, automatic enablement, and live activation. Native harness reasoning/tool output remains outside Sum’s control.

Deferred to Follow-Up Work

Native sidebar grouping is a capability-gated stretch after the grouped Sum view works. Historical per-lane analytics requiring new provenance storage are outside this projection change; missing factory attribution remains explicit.

Key Technical Decisions

KTD1KTD2KTD3KTD4KTD5KTD6KTD7KTD8KTD9

KTD1. One pure classifier, separate source adapters

Create a small presentation package for typed source facts, action owner, presentation kind, reason, stable identity, and detail references. It imports neither returns nor ask nor CLI. An inboxview adapter loads records and canonical obligations; the returns pump passes its already-derived obligations to the same classifier. This prevents the existing ask→returns dependency from becoming a cycle. Untrusted prose never drives priority or authority. Governs R1, R2.

KTD2. Tolerant presentation reads with explicit gaps

Use a presentation-only snapshot reader that returns readable task rows plus per-source errors and known/unknown counts. Keep store.AllTasks fail-closed for mutation callers. Reuse bounded context detail/paging shapes. Existing record fields retain their shape; explicit compact views add corrected owner/presentation semantics rather than dropping answered questions from legacy records. Governs R3, R5, R7.

KTD3. Sum owns grouping and explicit refresh

The grouped CLI view and terminal renderer share the snapshot model and canonical project keys from saved task.project. Empty project becomes standalone; host/owner/repository distinctions survive. Use view-local selection and collapse state, identity-bound detail/back, and an explicit refresh command. A small keyboard command loop is sufficient; no polling or new terminal framework is required. At 80×24, page routine rows and expose full question detail. Herdr Projects provides ordering inspiration, but its workspace-moving/ticker workaround is excluded. Governs R3, R5, R6, R7.

KTD4. Repair the native boundary before claiming native UX

Correct metadata inbox so it never calls Sync; it renders the grouped snapshot by default, with an explicit native-open option when the supported schema permits it. Reuse the inbox plugin manifest for that open action. Herdr 0.9.0 is the repository pin; fake support or the installed --skill text does not prove popup/grouping APIs. Capability discovery belongs to explicit setup/write boundaries, with saved capability results for read-only status. Metadata writes use verified machine/session/pane/occupant records, an instance-derived source, and comparison against successfully applied tokens. Disable clears only proven owned keys; failed clears remain diagnostic. Ambiguous legacy sum:.sum keys are preserved and reported. A disabled projection does not write. Add bounded post-commit projection after authorized domain writes and native events, including worker ask/report, without granting those callers coordinator authority. Use the existing successful mutation/event boundaries; reads never trigger it. Projection failure records degradation without undoing or failing the saved domain operation. Governs R5, R8.

KTD5. Recipient episode and consumption coverage are distinct

Add one versioned recipient sidecar in the existing delivery bookkeeping area, keyed by canonical recipient and verified incarnation. It stores the current episode/delivery ID, exact prepared claim references, submission phase, and presentation-consumed identities, a monotonic episode generation, and bounded exact receipt fingerprints. Priority delivery uses existing per-obligation attempts and never overwrites the outstanding routine episode or its recovery identity. Only an absent wake file means no episode: unreadable, malformed, symlinked, directory, unsupported-schema, or wrong-installation/recipient state blocks admission with a diagnostic. Keep existing per-task returns.json attempts authoritative and unchanged in vocabulary. The coverage set contains only still-relevant source identities, not message bodies or an append-only event history; prune only after canonical closure is successfully established. If a source is unreadable, retain its coverage and expose the gap. A routine latch suppresses new external routine prompts, not canonical obligations. Worker answer/refresh routing remains outside this latch. Governs R9, R12, R13.

KTD6. Ordered durable writes, one admission path, exact consumption

Keep lock order: shared compatibility lock → canonical recipient lock → store lock. Never hold the store lock across Herdr calls. Before a possible prompt, persist episode preparation, persist every covered per-task in-flight attempt, then persist submission intent. Only then call Herdr; finalize attempts before the episode outcome. This ordering preserves old readers’ uncertainty even though the writes are not one transaction. Any partial claim or possible submission requires conservative inspect/reconcile; no automatic resend follows a crash. A write error can follow a successful rename (for example directory sync failure); reload persisted identity under the locks before deciding recovery, without assuming no commit or resending. Both inline presentation and external prompts pass through this admission policy. Inline command output never consumes an outstanding episode implicitly.

A read response returns an opaque boundary binding installation, recipient/incarnation, episode, task/source identities and revisions, with explicit included/omitted coverage. The coordinator-only consume write validates that boundary under the same lock order and records only its included valid identities. A stale or partially unverifiable boundary returns an explicit refusal without widening coverage. A successful receipt updates coverage and closes only its exact episode in one recipient-file replacement; uncovered arrivals stay eligible for the next supported pass. It changes no per-obligation attempt and never calls attention.Seen. Retain bounded exact receipt fingerprints separately from prunable source coverage. Repeating a retained exact receipt returns its prior result without writes, including after the next episode starts. An older generation outside retained receipt coverage returns explicit expired/no-op, never adds coverage or closes the current episode; changed coverage under a retained consumed episode identity is refused. This is an authorized presentation attestation, not proof of comprehension. Governs R9, R10, R12.

KTD7. Gate protocol support and state the old-helper boundary

Declare a wake-protocol capability in the release contract, verified from the target tree or actual checkout binary using the machine-identity compatibility pattern. Enable new admission only with a capable selected runtime and an adopted coordinator contract. New code must refuse an incapable update/rollback target while an outstanding or uncertain new-protocol episode cannot be safely reconciled. Final downgrade validation and runtime selection share the exclusive delivery compatibility lock, ordered after the existing activation lock and before recipient/store locks. Admission rechecks selected-runtime capability and adoption after acquiring its shared compatibility lock, including a capable helper started before a runtime switch. External target probes remain outside the store lock. After explicit reconciliation, eligible legacy operation may resume with legacy presentation behavior; preserve the sidecar and all submitted/uncertain attempts. Direct older helper calls cannot be made coalescing-aware by this flag or by locks. Test and disclose their supported legacy behavior, and require explicit reconciliation before reactivating a preserved new episode after legacy operation. Governs R12, R13.

KTD8. Factory deltas are scoped evidence projections

Use existing factory occupancy for the current lane; use retained task, candidate, PR observation, and cleanup evidence for outcomes, including archived tasks. factory.Merge returning merged:true is a request result, not observed merge proof. Deduplicate outcomes by canonical repository and PR identity, retaining task/candidate/time references. Do not infer historical factory membership from project membership after a lane is removed: label a supported outcome as a project outcome unless retained records prove factory attribution. Unknown intake and freshness remain visible. This adapts OpenRig’s outcome-first presentation without its mission/daemon model. Governs R14, R16.

KTD9. Caller-held vector coverage, never a hidden last-seen marker

A versioned digest envelope binds installation and canonical project to per-task/source cursor leaves and stable outcome identities actually rendered. Reuse task counters/revisions as leaf evidence, not as a global clock. Bound each response and token; when a page cannot carry more coverage, return continuation/resync explicitly and leave the excess uncovered. Source shrink, replaced history, unsupported version, foreign scope, or missing coverage yields resync rather than an empty delta. Global decision/exception counts come from the complete readable snapshot before paging, with unknown coverage reported separately. If bounded tokens cannot retain earlier coverage, label a full resync rather than claiming repeated historical outcomes are new. Partial reads advance only successful included leaves; new sources remain new. Keep this envelope separate from the authoritative wake-consume receipt, sharing identity/validation utilities where appropriate. It is not persisted by a read. Governs R5, R15, R16.

System-Wide Impact and Rollout

  • CLI/full-output consumers keep existing defaults; new view options are explicit. Proposed command names below are design additions, not claims about today’s CLI.
  • All coordinator delivery entrances—task writes, pump, init, bind, and native events—use the same admission path. Worker-directed answer and refresh delivery keep their prior behavior.
  • Instruction changes use existing contract revision and refresh/adoption. Running coordinators do not adopt edited files automatically.
  • Metadata capability/ownership changes are confined to opted-in write boundaries. Human themes, keybindings, rows, and notification choices remain user-owned.
  • Runtime compatibility is reviewed alongside state persistence. Rollback must preserve evidence even when a previous helper cannot provide the new presentation behavior.
  • Every child updates the relevant help and feature-map rows; policy changes require independent coordinator review under VERIFY.md. No child updates the live installation.

Deferred Implementation Checks

  • Verify popup/split and optional repaint support against the supported Herdr schema in an isolated lab. Plain grouped output remains deliverable when native capability is absent.
  • Choose final flag spellings, cursor encoding and response/token bounds while implementing the contracts in KTD3, KTD6 and KTD9. Tests must assert explicit truncation/resync and never silently discard live coverage.
  • Capture the actual repeated-wake baseline using barriers and fake events before changing admission. The source hypothesis is not a production incident claim.
  • Establish measured counts and native/harness results during implementation. No runtime or verification result is claimed by this plan.

  • Crashes and sync errors after receipt replacement but before response replay safely; unknown execution retains its capacity reservation.
  • Supported old helpers retain submitted/uncertain attempts and opaque wake files in both old-created and candidate-created homes; legacy prompts are explicitly reported as uncoalesced.
  • Disabled hooks and missed events leave inspectable work plus a bounded explicit next-pass route, with no timer or recursive pumping.

Verification

#240a closes only after episode storage, consumption, compatibility and recovery are reviewed together; priority is still a separate deliverable.
