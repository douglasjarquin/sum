# Delivery pipeline

Every task that ends in a GitHub PR passes nine delivery gates: Intent, Rebase, Review, Test, Document, Lint, Push, PR, CI.
The order and the display names are one table in `go/internal/pipeline/pipeline.go`; a record always carries one row per gate.
Rows are derived from the task's own records, never set by hand, so the table cannot drift from the evidence it summarises.
The record is a pipeline.json file beside the task.json under the task record.
The implementation is `go/internal/pipeline`, registered as commands in `go/internal/cli/pipeline.go`; `go/internal/prcmd/pr.go`, `go/internal/verifycmd/verify.go`, `go/internal/review/review.go`, and `go/internal/report/report.go` re-derive the record after they change the facts it reads.

All nine gates run. Intent, Review, and Test read facts sum already holds. Rebase, Lint, Push, PR, and CI run a command of their own and record what it observed; Document audits the candidate's own contract.
`sumctl pipeline run TASK_ID` drives the coordinator-side gates in order, through opening the PR and reconciling it, and stops at the first failure. Review stays outside it: a review belongs to a separately launched reviewer pane, and no runner may stand in for it.
The intended pre-publication contract is Intent, Rebase, independent Review, Test, Document, Lint and Push before PR creation, followed by CI after the PR exists.
Ordinary publication should wait for the adopted pre-publication evidence from those gates, while the current record and runner do not yet enforce that full admission decision.
Later #158 phases own the stricter candidate and policy admission, so this documentation records the intended contract without claiming that enforcement is already fixed.

The PR gate reads `gh pr list --head BRANCH --state all` before it creates anything. A pull request already at the candidate, or any still open on that branch, is adopted rather than duplicated, so running `pipeline run` twice opens nothing the second time. A branch whose only pull requests are closed is refused, because a closed PR is not permission to open another; the refusal blocks the PR row with its reason until the coordinator passes `--allow-new-after-closed` or opens one themselves. A `gh pr create` that times out or prints output sum cannot read asks GitHub again before calling itself failed, since a timeout does not prove nothing was created.
The body sum generates states the approved intent, the worker's changes, what the coordinator's own gates recorded, and the limitations the handoff named. It carries neither the pipeline table nor the evidence block: the reconcile that follows publishes both into their own marked blocks. The body is kept at `.sum/tasks/TASK_ID/pipeline/pr/body.md`, and `--title`/`--body-file` replace what sum would have written.

Rebase observes and never rewrites. There is no `--apply`, because rewriting the task branch means force-pushing over a checkout the worker still holds, and that is the force-reset the operating contract forbids. A branch that is behind stays the worker's to rebase.
Push is the only place sum writes to a remote. It is a plain fast-forward push of the branch the worker already owns, never `--force`, never `--force-with-lease`, and never a delete.
Lint runs whatever lint task the project itself declares, discovered in that order as a mise task named `lint`, an npm script `lint`, or a `make lint` target.
A project that declares none is `not_declared`, which is not a failure.
sum itself declares `mise-tasks/lint`: `gofmt -l` and `go vet` over `go/`, and basedpyright on `.agents/skills/verify/scripts`, `.agents/skills/evidence/scripts`, `.agents/skills/maintain-verification/scripts`, and `.agents/skills/create-verification/scripts`.
When a project's lint is also part of its own `verify` aggregate it runs twice, once inside `mise run verify` and once as this gate; sum does not try to detect that overlap.

CI is observed, never watched. sum runs no daemon and polls nothing, so the checks are read whenever sum is already talking to GitHub about the PR: `pr reconcile` reads them after saving the PR observation and before the publications, and `sumctl pipeline ci TASK_ID` reads them again on demand. The row's time is when the checks last changed to what they say, so a green row means green as of the time shown; the instant of the last read is that row's `at` in `pipeline show`. Re-reading checks that have not moved renders an identical row, so the republish that follows is `unchanged` and edits nothing.
The scope is the checks GitHub marks required, mirroring what GitHub itself gates a merge on. A repository that marks none falls back to every check and the row says so rather than reading as a narrower pass than it is. A PR with no checks at all is `not_declared`, which is not a failure.
The gate binds to the PR's head SHA rather than the worker's candidate, because CI runs on what was pushed. After a new push the row reads as unobserved until the checks are read again, instead of showing the previous head's result. A merged PR keeps its last observation.

Each project keeps owning its own `VERIFY.md` and `mise run verify`, which work in any clone without sum. The pipeline gates sit around that contract and never edit it.

The table is the coordinator's record of what has run. It is not verification, review, or a merge decision, and only the user merges.
