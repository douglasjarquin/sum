# Native acceptance

The [issue #348 evidence](verification/issue-348.md) separates package/tooling proof from authenticated native acceptance.
Static instruction checks, CLI help, and offline fixtures cannot substitute for an authenticated conversation.

Run each scenario below from the actual candidate in a supported HC-backed Herdr terminal.
Record app/HC/harness versions and artifact identity, launch commands, exact addresses/parentage, candidate inputs, observed incoming messages, reports/output, and limitations.
Use a disposable project for the deliberate finding and independent scratch sessions/XDG paths for lifecycle cases.
Do not restart the user's shared core or mutate foreign terminals.

| Scenario | Observable result |
| --- | --- |
| Ordinary entry | Existing native terminal, same usual agent/conversation, task requested without Sum build/init/setup |
| Native parentage | Actual lead child, notifications enabled, parent-linked lifetime |
| Background work | Real project command and interactive reviewer run while lead remains available for messages |
| Success and failure | Native test exit notifications plus inspected actual output/status for both zero and nonzero exits |
| Reviewer return | Report saved, then explicitly sent to actual parent input without collection or copy/paste |
| Follow-up | Completed reviewer closed after report collection; fresh fixer receives findings, then fresh reviewer checks the corrected frozen candidate and refreshes affected evidence |
| Helper question | Question or blocker leaves worker unfinished; actual answer saved, sent, and visibly applied without invented approval |
| Roles and isolation | Helper remains bounded after reading entry; separate writer worktrees and stable validation inputs |
| Startup uncertainty | Live terminal with undelivered assignment distinguished; inspect before recovery, no blind duplicate |
| Busy/blocked/timeout | Native wait/send semantics, no forced dialog input, timeout treated as check-in; idle/done without a usable report does not trigger completion cleanup |
| Missing prerequisite | Missing HC/connection/identity/status, old TUI, and unsupported harness receive truthful launch guidance |
| Resume and shell lifetime | Actual program/conversation inspected after interruption or shell recovery; lead delegates further investigation and fixes while bounded workers resume only their own assignments |
| Completion | Every required result resolved against final stable candidate, within publication authority |
| Cleanup | Completed builder closes after report collection while PR remains open; exact owned terminals removed, required child results accounted for, reports/output/branches/worktrees and unrelated terminals preserved |
| Legacy adoption | Separate checkout leaves legacy callbacks, tasks, records, and worktrees intact |
| Scope preservation | Excluded Bot/shared contracts unchanged; readable legacy lane guides; independent tooling/site works |

All authenticated native rows remain unrun in the API development conversation because it has no HC_TERMINAL_ID.
This gap does not authorize a custom transport; issue Phase 1 permits implementation with the limitation explicit.

## Review and PR evidence acceptance

Use the final candidate in at least two available harness/skill-stack combinations, recording which combinations actually ran.
Use a disposable target with a known inventory of setup, readiness, checks, mapped scenarios, and teardown so missing table rows are observable.
Include visual and CLI/API changes across the runs.

| Scenario | Observable result |
| --- | --- |
| Review handoff | Builder report is followed by a distinct reviewer launch; substantive saved review reaches the actual lead |
| Review correction | A seeded finding returns to the builder; corrected candidate receives affected checks and follow-up review |
| Complete PR accounting | The PR accounts for every prescribed target step, with aggregate coverage identified and unrun manual scenarios explicit |
| Published behavior evidence | Real before/after screenshots or redacted command/request-response text is accessible on the PR and names the actual base/candidate |
| Baseline unavailable | Available after evidence is clearly labeled with the real reason the base could not run |
| Publication failure | Draft retains the gap and available proof without claiming completion |
| Candidate changed | Old evidence is retained with its identity but cannot close the new candidate's review or verification obligations |

Record observed outcomes and limitations in [review and PR evidence](verification/review-pr-evidence.md).

Invoked implementation, verification, and shipping workflows must preserve the same role boundary: the lead launches the worker and returns to messages while that workflow runs.
